# SP1 · T0.3 — frozen spec: redirect shared localStorage writes through `src/stores/*`

Status: frozen 2026-07-25. Implements PLAN.md T0.3. Work order/inventory:
`docs/sp1/store-inventory.md`. **Behavior-preserving refactor.** No feature
change, no UI change, no data-shape change.

## Goal

Every write and delete of a *shared-data* `rxt-*` localStorage key goes through a
`src/stores/<key>.js` module instead of touching `localStorage` directly. After
this task, `grep` for `setItem`/`removeItem` on an in-scope shared key outside
`src/stores/*` returns nothing (excluding test files and the store-internal
fallback path described in §4).

The app must behave **byte-identically** afterwards: same keys, same JSON,
same merge/replace outcomes, same quota-recovery behavior.

## 2. Store API change — split replace from merge (do this FIRST)

Today every module's `write(userId, value)` merges the incoming value with what
is already stored. That is correct for **sync hydration** but WRONG for local UI
writes: `App.jsx` does `safeSetItem("rxt-block-objectives", next)` after a
delete, and a merging write would resurrect the deleted objective. Routing UI
writes through the current `write()` would be a silent data bug. So:

In `src/stores/base.js`:
- keep `writeJson(userId, logicalKey, value, { fallback, merge })` as-is.

In **every** module (the 8 existing + the 2 new):
```js
// authoritative replace — what local UI writes do today
export function write(userId, value) {
  return writeJson(userId, key, value);          // no merge fn
}
// merge with stored value under this key's conflict policy — sync path
export function merge(userId, incoming) {
  return writeJson(userId, key, incoming, { fallback, merge: <policyFn> });
}
```
Both must `notifyStoreChanged` (they already do, via `writeJson`).

Update the existing store tests (`src/stores/*.test.js`) that assert merging
behavior to call `merge(...)`, and ADD one `write()`-replaces test per module
family proving a removed entry stays removed (this is the regression guard for
the delete bug above). `base.test.js` subscribe/notify assertions must cover
both `write` and `merge`.

`src/stores/index.js`: export the two new modules.

## 3. Call-site redirect strategy

Do NOT hand-rewrite all ~90 shared-key call sites individually. Route through
the existing per-file storage helpers, which is smaller, safer, and reviewable:

### 3a. `src/App.jsx` (~72 shared-key sites)
`safeSetItem(key, value)` (line ~2892) becomes the single routing point:
- Build a logical-key → module lookup (import `* as stores from "./stores/index.js"`
  or a small `storeForKey(key)` helper exported from `src/stores/index.js` —
  prefer adding `export function storeForKey(logicalKey)` to `index.js`).
- If a module owns `key`: call `mod.write(null, value)` and return `true`
  (return `false` if it throws).
- Else: the existing raw `localStorage.setItem` + quota-recovery path, unchanged.
- `sSet` already delegates to `safeSetItem` — leave it.

Then mechanically rewrite the **direct** `localStorage.setItem("rxt-<in-scope
key>", JSON.stringify(x))` calls in `App.jsx` to `safeSetItem("rxt-...", x)`
(note: `safeSetItem` stringifies, so drop the `JSON.stringify`). Same for any
`localStorage.removeItem` on an in-scope key → route to the store as a write of
the module's `fallback` value ONLY if that is what the current code means;
otherwise flag it as a deviation rather than guessing.

Leave out-of-scope keys' direct calls alone.

### 3b. `src/Tracker.jsx`
Its local `sSet(k, v)` (line 7) gets the same lookup-and-delegate treatment,
raw-localStorage fallback preserved. Lines ~3937/3974 write local-preference
keys — unchanged.

### 3c. `src/supabase.js` (highest priority — runs on every sync)
Lines ~364/460/480/491/498/505/512/519/571/597. These already compute a merged
value with their own merge fn and then `setItem` it. Preserve that exactly:
replace only the final `localStorage.setItem(...)` with the module's
**`write(null, merged)`** (replace) — do NOT swap their inline merge for the
store's `merge()`, because argument order differs between the two sides
(`mergeTerms(local, incoming)` vs `mergePerformance(cloud, local)`) and changing
it would alter conflict outcomes. Keep every `try/catch` exactly as-is.

### 3d. Remaining files

## 4. userId / namespacing — explicitly deferred

`base.physicalKey(userId, key)` namespaces to `rxt:<uid>:<key>` when `userId` is
truthy. **The app today writes plain, non-namespaced keys everywhere.** Passing a
real `userId` at some call sites and not others would split the data in half.

Therefore: **every call site in this task passes `null` as `userId`.** Do not
thread a real user id anywhere, do not add a "current user" global. Namespacing
is wired in T0.4 with the hooks. Add a one-line comment at the `safeSetItem`
routing point recording this.
